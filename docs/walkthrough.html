Consistent multi-agent work system: phases 0 to 4

What was built in each phase, how each layer works and the principle behind it. Diagrams are inline, so this file works offline on a phone.

Overview: the layers

Each phase sits on top of the one below. Phase 4 is the orchestration layer: several AI agents work in parallel, each on its own branch, and their results land in main in order and only after validation.

Phase 0: replicated, sharded key/value store

Problem: machines fail and networks drop messages. How do reads and writes of a key stay correct, and how does it scale out?

  • At-most-once: every request carries (client id, sequence number). The server recognises a resent request and returns the earlier reply, so a non-idempotent operation such as 'add 1' is never applied twice.
  • Paxos replicated log: a shard group has 3 replicas. A write needs a majority (2 of 3) to agree on a log slot; all replicas apply the log in the same order. Same start state plus same deterministic commands gives same state. One replica may be down. This is where linearizability comes from.
  • Sharding: keys are hashed to replica groups. A shard master holds the map from shard to group and can move shards live (reconfiguration).

Phase 1: making the store usable from outside

No new algorithm. Two conditional writes were added, plus an HTTP gateway:

  • CompareAndSet(key, expected, new): writes only if the key currently holds expected.
  • PutIfAbsent(key, value): writes only if the key does not exist.
  • Gateway with replica fault injection (for tests) and an optional write-ahead log so a restarted cluster keeps its data.

These two operations are the foundation of everything above. Because they are linearizable in the replicated store, 'many writers race for one thing and exactly one wins' is guaranteed by the store. Versioning, leases and claims are built on that. There are no distributed locks.

Phase 2: the versioned workspace

Idea: git's model on this store, where the only mutable things are a few compare-and-set refs.

  • Objects are named by the hash of their content: immutable, deduplicated, and writing the same object twice is harmless, so network retries are safe.
  • A fork is one new ref pointing at the current main commit: O(1), nothing is copied, so every agent can have a branch.
  • Refs move only by compare-and-set, so main's history is a single line.

submit lands an agent's work on main:

  • Three-way merge: per file, compare base (fork point), mine and theirs. Only one side changed: take it. Both changed: line-level diff3; non-overlapping edits merge, overlapping ones conflict. Renames are tracked so edits to the old path follow the file.
  • Stale-read detection: an agent reads a counter (5) and writes 6 elsewhere; meanwhile main's counter becomes 7. No file overlaps, so text merge is silent, but the decision is based on old data. The workspace records what was read and submit checks it. In a test with 8 agents doing read-modify-write, skipping this check lost many increments; with it, none.
  • The CAS is the linearization point. The merge is computed locally; it only takes effect at the one compare-and-set of main. If it fails, main moved: retry on top of it. No lock, no deadlock.

Phase 3: local sync

Problem: a person edits in their own editor while cloud agents edit the same branch. A real folder is treated as one more client of the workspace, reusing the same fetch, merge, CAS, retry logic. The folder remembers the branch commit it last synced (the base), and every decision is made relative to it.

  • Offline edits for days still merge correctly, because the base is the last synced commit, not 'now'.
  • Conflicts never lose data: standard markers are written and push is blocked until you resolve.
  • A local rename (a file disappears and an identical new one appears) is detected as a move, and others' edits follow it.

Phase 4A and 4B: workers, task graph, scheduling

Problem: turn one goal into several agent runs that do not step on each other.

  • Worker isolation: a worker writes only to its own branch and never to main. That keeps 'what may enter main' in one place, which validation, queueing and recovery rely on.
  • Tool loop (LoopWorker): send the conversation to the model, get tool calls back, run them, feed results back, repeat until finish. Only 6 simple file tools (list, read, write, replace_in_file, delete, move) because small models do better with few clear tools. Every error returns as text so the model can correct itself. A commit happens only on finish. CliWorker instead checks the branch out into a folder, runs an existing command-line agent and pushes the result.
  • Scheduling by scope: each task declares the paths it will change. Disjoint scopes run in parallel. Overlapping ones run in order and start from a main that already holds the earlier work. This avoids conflicts by scheduling instead of resolving them afterwards.
  • Path leases: a run-time blackboard in one key, changed by CAS, advisory and expiring. Of racing overlapping claims exactly one is granted; a crashed agent's lease just expires.
  • Audit: afterwards, what the agent really touched is compared with what it declared. Strays are logged, and a stray landing inside another live lease is flagged as a collision (a likely conflict).
  • Planner: a model produces JSON tasks; it is validated (duplicate ids, unknown dependencies, cycles) and errors are sent back for a retry, because small models often produce invalid JSON.

Phase 4C: merge queue and escalation chain

Why: a conflict-free text merge is not necessarily correct (two files each defining the same function name). So the merged result is validated before main moves.

  • Validate hook before the CAS: submit merges, hands the candidate commit to the validator, and only then does the CAS. If main moves meanwhile and the merge is redone, the validator runs again on the new candidate, so what was validated is exactly what lands. Main holds only approved states.
  • Validators: an always-on guard rejecting new conflict markers; CommandValidator writes the candidate tree to a temp folder and runs a command (for example the test suite), exit 0 means accept.
  • The queue's lock is not the source of correctness. It only serialises validate-and-land inside one process. Correctness comes from the final CAS; several queues just retry.
  • Why these stages: auto merge handles most cases. The merger agent handles 'both intents are fine, the text collides'. Redo handles decisions based on stale information, which merging cannot repair, so it skips the merger. The human record is the backstop; the branch is kept with a durable record of everything tried.

Phase 4D: reliability and the end-to-end orchestrator

What a crash loses: uncommitted edits and the model conversation (memory). Safe in the store: commits, branches, main. Left behind: leases, which expire. The design goal is that rerunning the same command continues the run.

  • Numbered tool calls (at most once): same idea as phase 0's (client, seq). Call n runs once; a resend returns the recorded result; a skipped number is refused. Needed because replace_in_file would fail the second time. Also what a remote agent over a lossy link needs.
  • Checkpoints, commit first then record: commit the overlay, then write one record (sequence, commit, conversation, recent results). If the process dies between the two, the branch is ahead of the record. On reopening the branch is rolled back to the recorded commit, because the record states what the agent knew when it made that commit.
  • Durable LoopWorker: the conversation, step count and token counts are restored, so the model sees an unbroken history. A finished task stores its result and is not run again.
  • Task claims with epochs: one live owner per task, claims expire. Taking over an expired claim raises the epoch. Renew, complete and release must present the epoch granted, so an owner that was merely slow (not dead) cannot overwrite the new owner's work. This is a fencing token. Claims are taken before path leases because the lease key is the task id and acquiring it would refresh another owner's lease.
  • Heartbeat: the scheduler renews claims and leases of running tasks every third of the claim lifetime. If a renewal fails the task is marked lost: it is not landed and not completed.
  • Completion is not in a finally block: a killed process would not run it either, so tests that simulate a kill see the same behaviour.
  • Orchestrator: plans once (stored with put-if-absent, so two orchestrators agree), schedules with claims, lands through the merge queue and records the result. Rerun with the same run id: completed tasks are reused, live owners left alone, expired claims taken over and resumed, and a task that landed but whose completion record was lost lands as a no-op.
  • Last-moment fence: the claim is checked again inside submit's validate step, just before the CAS on main. A replaced owner is refused at once with no merger, redo or escalation. A small window remains because the store has no transaction across claim and main; whatever lands there was still merged and validated against the main it replaced, so the cost is duplicate work, never a wrong main.
  • Later hardening: task names are namespaced per run (branch RUN-TASK, so runs can reuse names); CliWorker can push progress at an interval and a retry is told which files an earlier attempt already changed.

How it was tested

  • Scripted fake models, so tests are deterministic and free.
  • Injected CAS races: a store wrapper that changes a key at an exact moment to force 'main moved during merge'.
  • Threaded tests with the landing history recorded in CAS order, checking every move of main was an approved state.
  • Random edit storms through every escalation stage, checking markers never reach main and each successful task appears exactly once.
  • A non-catchable exception stands for 'the process died'; real subprocesses killed with os._exit against the real cluster; reference-model comparison for claims.
  • Mutation testing: operators in the code are flipped automatically and the suite must notice. Survivors are reviewed; most are equivalent mutants.
  • Result: 323 workspace tests; a real run with the claude command-line agent landed two parallel tasks through validation.

Principles that run through all phases

  • Correctness comes from compare-and-set, not from locks.
  • Immutable and idempotent things make retries safe (content-hashed objects, numbered calls, no-op landing).
  • Processes hold no essential state. Plan, claims, checkpoints and results are in the store, so a rerun continues.

Known limits

  • The merge queue is a library, not a service; several processes using it are safe but share no common queue order.
  • The merger only sees conflicted files; cross-file semantic problems are left to the validator.
  • A redo discards partial work.
  • The claim fence and the CAS are not one atomic step; the worst case is duplicate work.
  • LoopWorker with a local Ollama model has not been run against a real model yet; the real-model check so far used the claude command-line agent.
